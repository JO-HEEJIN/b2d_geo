# 진행상황 보고 검증 규칙 (모델 무관)

목적: "완료했다"는 주장을 신뢰 가능하게 만드는 최소 요건. 이 세션에서
보고가 틀렸던 실례 3건이 규칙의 근거다.

## 완료 주장의 3요소 (하나라도 없으면 미완 취급)

1. **수치** — 검증 하니스/카운트 결과 (800/800, 13,338,839행=원본 일치).
2. **경로** — 근거 파일·로그 위치 (커밋 해시, 하니스 출력 경로).
3. **재현 명령** — 사용자가 직접 돌려볼 수 있는 한 줄
   (`curl ... /v1/geocode?q=...`, `go test ./internal/address/`).

## 오보 실례 대장 (이 세션에서 실제 발생)

| 사례 | 무엇이 틀렸나 | 교정 규칙 |
|---|---|---|
| **유령 서버** | 하니스 9.5%의 원인이 코드가 아니라 "bind: address already in use" — 구버전 서버가 응답 중. 신코드 검증이라 믿은 것이 구코드 측정 | 재기동 후 검증은 `pgrep` PID 확인을 보고에 포함 |
| **오탐 HEALTHY** | 워처의 `grep X \| cut && echo OK`가 파이프라인 종료코드 함정으로 크래시를 HEALTHY로 보고 | 자동 판정 스크립트의 판정 grep은 단독 실행 + 크래시 패턴을 명시적으로 나열 |
| **전송 완료 오인** | rsync가 옵션 에러로 즉사했는데 백그라운드 완료 통지만 보고 성공 처리 → 원격 파일 0 | 전송·적재류는 종료코드가 아니라 **원격 카운트 대조**가 완료 기준 |

## "이상 없음 0건" 의심 규칙

- 실패·미해결·알려진 이슈가 **하나도 없는** 완료 보고는 검증 부족의 신호다.
  이 세션의 정직한 보고에는 항상 잔여 항목이 있었다 (QA 보고의 UNRESOLVED
  4건, 지적도 8시도 잘림, 논문 PENDING 목록).
- 검수 보고가 전부 PASS면 검수 범위를 물어라 — 무엇을 **안** 봤는지가 정보다.

## 사용자 스팟체크 질문 (복붙용)

1. "그 수치 어디서 나왔어? 로그 경로 줘."
2. "내가 지금 직접 확인하려면 무슨 명령 치면 돼?"
3. "지금 켜져 있는 프로세스·감시·과금 자원 전부 나열해."
4. "이번 보고에서 검증 안 된 부분이 뭐야?"
5. (재기동 후) "응답한 프로세스 PID가 새 빌드 맞아?"

## 보고 작성 규칙 (모델 측)

- 진행 중 작업은 %가 아니라 **관측값**으로 (72만/89.8만 행 — %는 파생).
- 실패는 원문 그대로 인용 (에러 메시지 요약 금지).
- 이전 보고를 정정할 때는 무엇이 왜 틀렸는지 명시 — 정정 이력이 신뢰 자산.
