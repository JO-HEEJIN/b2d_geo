# Effort / 모드 선택 기준표 (모델 무관)

목적: 추론 강도(effort)와 병렬 오케스트레이션(멀티에이전트) 사용 기준.
비용 실감은 2026-07-05~12 세션 실측.

## 기준표

| 수준 | 언제 | 이 세션 실례 |
|---|---|---|
| **낮음** | 정형·기계적: 형식 변환, 파일 이동, 카운트 검증, 문서 받아쓰기 | 이미지 추출, todo 체크 갱신, 커밋 메시지 |
| **중간** | 사양이 명확한 일반 구현·조사 | 로더 구현(명세 문서 존재), API 핸들러, 라이선스 확인 |
| **최고** | 설계, 원인 불명 디버깅, 검수 재검증, 실험 해석 | 파서 설계, 14%→100% 진단, OOM/CUDA assert/cgroup 3연쇄 디버깅, QA INFO-1 반박 |

원칙: **막히면 낮추지 말고 올린다.** 디버깅 미궁에서 낮은 effort로 반복
시도하는 것이 최대 낭비다 — 이 세션의 성과 대부분은 "한 번의 정확한 진단"
에서 나왔다 (포트 유령, 1M 잘림, 커넥션 고정).

## 병렬 에이전트(포크/서브에이전트) 비용 실감

- **포크 1회 ≈ 90만 토큰** (실측: 스킬 감사 89.3만, 인수인계 89.5만 —
  부모 컨텍스트 전체 상속 비용).
- 따라서 포크는 **컨텍스트 상속이 필수인 작업**에만: 세션 지식의 증류
  (인수인계, 감사, 회고). 상속이 불필요하면 신선한 서브에이전트가 훨씬 싸다
  (Phase 4 에이전트 — 지시서 경로만 주면 충분했음).
- 병렬화 가치가 있는 형태: ① 독립 검수 N-렌즈 (3-렌즈 QA) ② 사양 명확한
  대형 구현을 메인 작업과 병행 (Phase 4) ③ 세션 증류 문서 다발.
- 병렬화 금물: 같은 파일을 두 주체가 만지는 구조 — 이 세션은 server.go
  소유권을 사전 분할해 회피했다. 분할 불가면 순차.

## ultracode(최고 강도 + 오케스트레이션 상시) 사용처

이 세션에서 켠 구간: Phase 2·3·4 동시 진행일, ops 문서 스위트 제작일.
가치가 있었던 이유: 트랙이 3개 이상 병렬이고 각 트랙에 판단이 필요했음.
단일 트랙 정형 작업에는 과잉 — 기본 모드로 충분.

## 빠른 결정 규칙

1. 실패 시 재작업 비용 > 추론 비용이면 → 한 단계 올려라.
2. 두 번 연속 같은 방식으로 실패했으면 → 강도를 올리고 접근을 바꿔라.
3. 병렬화 전에 물어라: "이 에이전트에게 세션 맥락이 필요한가?"
   No → 신선한 에이전트 + 명세 포인터. Yes → 포크 (90만 토큰 각오).
