# 추론 과정 요구 문구 점검 (모델 무관)

질문: "추론/계획을 보여달라"는 요구가 언제 품질을 올리고 언제 형식이 되는가.
근거: 2026-07-05~12 세션의 실제 산출 대조.

## 가치가 있었던 추론 노출 (요구할 것)

1. **진단 서사** — 증상→가설→실측→판정 사슬.
   실례: 정확도 14% → "읍·면이 키에서 탈락" 가설 → 실패 표본으로 확인 →
   수정 → 100%. / GPU util 29% → RAM디스크 무효 → `data:` 시간으로 IO 배제
   → cgroup 13.6코어 발견. 이 사슬이 노출되면 사용자가 결론을 검증할 수 있고,
   틀린 가설(RAM디스크)이 기록으로 남아 재발을 막는다.
2. **트레이드오프 결정 근거** — 선택지·버린 이유 1줄씩.
   실례: 30→10 epochs (예산 $63 vs $14, 막판 기울기 손실 감수 명시).
3. **검수 반박 근거** — 검수자 지적을 수용/기각할 때의 실측.
   실례: QA INFO-1 기각 — set_limit은 커넥션 단위이므로 tx가 유의미.

## 형식화됐던 추론 노출 (요구하지 말 것)

1. 정형 작업의 번호 계획 나열 — "1. 파일 쓴다 2. 빌드한다 3. 커밋한다"는
   정보량 0. 매 턴 훅이 강제했으나 실제 가치는 대형 작업에서만.
2. 이미 결정된 사안의 사후 정당화 — 결론 먼저 내고 이유를 소급 작성.
3. 결과로 즉시 검증되는 작업의 사전 추론 — 빌드/테스트가 3초면 답한다.

## 권장 문구 3

- "**증상에서 원인까지의 사슬**을 실측값과 함께 보여줘" (진단 시)
- "선택지 각각을 **버린 이유 한 줄씩**과 함께 결정을 보고해" (설계 시)
- "그 수치의 **출처 경로와 재현 명령**을 붙여" (완료 주장 시)

## 금지 문구 3

- "모든 단계를 상세히 설명하며 진행해" → 정형 단계 나열로 토큰 소모
- "왜 그렇게 했는지 매번 정당화해" → 사후 합리화 유도
- "생각을 전부 보여줘" → 서사 아닌 독백 덤프 — 검증 불가능한 장문

## 원칙

추론 노출의 목적은 **사용자가 결론을 검증할 수 있게 하는 것**이다.
검증에 기여하지 않는 추론 텍스트는 비용이다. "how"가 아니라
"어떤 증거가 이 결론을 강제했는가"를 요구하라.
