# User Process Flow
# b2d_geo — 공공데이터 기반 위치 서비스 엔진

- 문서 버전: 1.0
- 작성일: 2026-07-03
- 기반 문서: 01~05 전체 (SDP, UML, SRS, BRD, Test Cases)

이 문서는 실제 사용자가 b2d_geo를 어떤 순서로 만나고 사용하는지를 서술한다.
v1에는 웹 콘솔이 없으므로(SDP 1.3 범위 외) 온보딩은 운영자 개입형이다.
이 제약을 숨기지 않고 흐름에 그대로 반영했다.

---

## 1. 페르소나

| ID | 페르소나 | 상황 | 핵심 니즈 | 대응 상품 (BRD 5.1) |
|---|---|---|---|---|
| P-01 | 프롭테크 백엔드 개발자 (김OO, 5년차) | 매물 DB 40만 건의 주소가 구주소/신주소/오타 혼재. 카카오 API 일일 제한으로 정제 작업이 수 주 소요 | 제한 없는 배치 지오코딩, 건별 신뢰도 점수 | Bulk |
| P-02 | 감정평가법인 IT 담당 (박OO) | 평가서 작성 시 주소 → PNU → 지적 확인을 정부 사이트 3곳에서 수작업 | 주소 한 번 입력으로 PNU/필지 폴리곤까지 | RealEstate |
| P-03 | 공공기관 전산 담당 (이OO) | 망분리 환경. 외부 API 호출 자체가 보안 규정 위반 | 오프라인 설치, 외부 통신 0건 증빙 | On-Prem |

## 2. 흐름 A — 온보딩 (전 페르소나 공통)

```
[1] 잠재 고객이 소개/영업 자료(D-08 벤치마크 리포트 포함)로 접촉
        |
[2] 운영자(Heejin)가 용도 확인 후 평가용 API key 발급
    $ b2d-keys issue --name "acme-proptech" --rate 10
    -> 평문 key는 이 시점 1회만 출력 (FR-61). 고객에게 안전 채널로 전달
        |
[3] 고객이 OpenAPI 3.1 스펙(D-05)과 curl 예시로 첫 호출
    curl -H "Authorization: Bearer mk_xxxx..." \
      "https://api.example/v1/geocode?query=경기도 하남시 미사강변대로 100"
        |
[4] 평가 기간 사용량은 /v1/usage 로 고객이 직접 확인 (FR-64)
        |
[5] 계약 전환 시 rate limit 상향 재발급, 계약서에 데이터 출처/면책/SLA 명시 (BRD 6절)
```

실패 분기: [3]에서 401이면 key 전달 오류 → prefix(앞 8자)로 발급 이력 대조.
429면 평가용 rate 초과 → 정상 동작임을 안내 (TC-A03 시나리오와 동일).

## 3. 흐름 B — P-01 벌크 주소 정제 (Bulk)

상황: 매물 40만 건 주소를 좌표+정규화 주소로 변환.

```
[1] 고객 시스템이 주소를 10,000건 단위로 분할 (FR-23 상한)
        |
[2] POST /v1/geocode/batch  (40회 반복)
    { "queries": ["서울시 강남구 ...", "하남 미사강변대로 100", ...] }
        |
[3] 응답: 건별 결과 배열. 각 건은 matches[] 또는 error
    - score 1.0 / 0.9: 자동 채택 (FR-22)
    - trigram 폴백 (score < 0.9): 고객 측 검수 큐로 분류
    - error: 원문 보존 후 수기 처리 목록으로
        |
[4] 고객이 pnu, bcode 필드를 자사 매물 테이블에 저장 (FR-21)
    -> 이후 필지 단위 분석은 /v1/parcel?pnu= 로 확장 가능 (업셀 경로)
        |
[5] 월말: /v1/usage 집계 = 청구 근거 (BR-06). 운영자가 수동 청구 (v1 범위)
```

설계 의도: [3]의 score 기반 3분류가 이 상품의 실질 가치다. 고객은 "몇 %를
사람이 봐야 하는가"를 API 응답만으로 결정할 수 있다. NFR-04(정답률 90%)가
지켜져야 이 흐름이 성립하므로, 정확도는 기능이 아니라 사업 전제다.

## 4. 흐름 C — P-02 감정평가 실무 (RealEstate)

상황: 평가 대상 부동산의 주소로 필지 정보까지 한 번에.

```
[1] 평가서 시스템에 주소 입력: "경기도 하남시 망월동 1105"
        |
[2] GET /v1/parcel/by-address?query=...   (FR-51, 내부적으로 geocoding 재사용)
    -> pnu, 지목, 필지 폴리곤(GeoJSON)
        |
[3] 폴리곤을 평가서 첨부 도면 레이어로 렌더링 (고객 측 지도 라이브러리)
        |
[4] 현장 조사 시 모바일에서 GET /v1/reverse?lat=..&lng=..
    -> 현 위치의 주소 + PNU 즉시 확인 (FR-30, FR-32)
        |
[5] 주변 상권 근거 자료: GET /v1/places/category?code=..&bbox=..  (FR-42)
    -> 반경 내 업종 분포를 평가서 근거로 첨부
```

주의 문구(계약/문서 명시 사항): b2d_geo의 필지 데이터는 공공데이터 기반이며
공부(公簿)의 법적 효력을 대체하지 않는다. 최종 확인은 정부 원천 시스템으로 한다
(BRD 6절 면책 조항의 사용자향 표현).

## 5. 흐름 D — P-03 온프레미스 도입 (On-Prem)

```
[1] 계약 후 설치 패키지 전달 (물리 매체 또는 기관 반입 절차)
    구성: b2d-server 이미지 + PostGIS 이미지 + 데이터 스냅샷 + docker-compose + 설치 문서
        |
[2] 기관 내부망에서 docker compose up
    -> 외부 통신 0건 (NFR-08). 보안 심사용 증빙: TC-N04 패킷 캡처 리포트 동봉
        |
[3] 기관 내부 시스템들이 내부 주소로 API 사용 (흐름 B/C와 동일 인터페이스)
        |
[4] 분기별 데이터 스냅샷 갱신: 새 스냅샷 반입 -> b2d-etl 오프라인 적재 (FR-07)
    -> 갱신 구독이 이 상품의 반복 매출 구조 (BRD 5.1)
```

## 6. 흐름 E — 운영자 내부 프로세스 (Heejin)

### 6.1 월간 데이터 갱신
```
[1] 매월 초: juso 변동분 공개 확인
[2] b2d-etl load --source=juso --month=YYYY-MM   (02 문서 시퀀스 3.2)
[3] 스키마 검증 실패 시: 적재 자동 중단 -> 명세 변경 여부 확인 (R-02) -> 파서 수정
[4] 성공 시: 샘플 5건 실측 대조 결과 확인 후 learning_log에 기록
[5] 분기: 상가(상권)정보 갱신 (동일 절차)
[6] gitnexus analyze 재인덱싱 (코드 변경이 있었던 경우)
```

### 6.2 신규 key 발급 / 폐기
```
발급: b2d-keys issue --name <고객> --rate <rps>   -> 평문 1회 출력, 해시만 저장
폐기: b2d-keys revoke --prefix <앞8자>            -> 즉시 401 (TC-A02)
```

### 6.3 장애 대응 (1인 운영 현실 기준)
```
[1] /v1/health 외부 모니터링 (uptime 체커) 알림
[2] 1차: 컨테이너 재기동. 2차: DB 연결/디스크 확인
[3] NFR-05 (99.5%)는 목표치이며, 계약상 SLA는 고객별 협의 범위임을 유지
    -> 1인 운영에서 지킬 수 없는 SLA를 계약서에 넣지 않는 것이 원칙 (BR-07)
```

## 7. 흐름 상 미해결 지점 (정직한 한계 목록)

1. 웹 콘솔 부재로 key 발급/청구가 운영자 수작업이다. 고객 3곳 초과 시 병목이
   되므로, 그 시점이 콘솔 개발(v2)의 착수 트리거다.
2. 결제 자동화 없음. v1은 계산서 수동 발행. Lemon Squeezy류 MOR 연동은 v2 검토.
3. 흐름 C의 [3] 지도 렌더링은 고객 몫이다. b2d_geo는 타일을 제공하지 않으므로
   고객이 오픈소스 지도(예: 자체 타일)나 기존 지도 계약을 보유해야 한다.
   영업 시 이 전제를 선제 고지한다.

## 증보 v1.1 (2026-07-03) — Phase 7 감정평가 모듈

### 흐름 C 확장 — P-02 감정평가사 공시지가기준법 실무
```
[1] 대상 필지 확정: /v1/parcel/by-address 로 PNU 확보 (기존 흐름 C[2])
[2] /v1/appraisal/land-use?pnu= + /v1/appraisal/land-features?pnu=
    -> 용도지역·저촉 면적비, 이용상황·도로접면·지형 (사실 확인)
[3] /v1/appraisal/standard-lots?pnu=&use_zone=...&land_category=...
    -> 후보 표준지 목록 (거리순). 비교표준지 "선정"은 평가사가 한다 —
       API는 후보와 사실만 준다 (BR-10)
[4] /v1/appraisal/official-price?pnu=<선정 표준지>
[5] /v1/appraisal/price-index?sigungu=&use_zone_class=&from=&to=&cumulative=true
    -> 시점수정 원자료 + 누적률(산식 병기)
[6] /v1/appraisal/sales?pnu=&radius=&from=&to= -> 그 밖의 요인 검토용 사례
    (location_precision 한계 notice 확인)
[7] 격차율 산정·평가액 결정은 평가사/PoC human gate 영역. b2d_geo 역할 종료
```
기존 수작업(정부 사이트 3곳 왕복) 대비 [2]~[6]이 API 6호출로 대체된다.
