# Cloudflare 캐시·요청 제한 운영 안내

작성일: 2026-09-12. **배포 전 기준의 설정 절차·검증 계획이다. Cloudflare 설정은 미적용이며, 아래 상태표는 배포 완료 보고가 아니다.**

관련 전체 설계: [ETL·시점 조회·데이터 공개](/Users/mac/dev/b2d_geo/docs/design/etl-temporal-architecture.md:505). Cloudflare는 캐시·앞단 보호, AWS는 Go API·PostGIS·무거운 ETL을 담당하는 방향이다. 지금은 Worker·Redis·Go 응답 캐시를 추가하지 않는다.

## 1. 현재 상태

| 항목 | 상태 |
|---|---|
| IP 요청 제한 | 기존 구현 유지: 프로세스당 IP 20 req/s, burst 40 |
| API 키 요청 제한 | 기존 구현 유지: DB의 `rate_limit_rps`, burst는 그 2배 |
| 인증 결과 캐시 | 기존 구현 유지: 기본 30초, `B2D_AUTH_CACHE_TTL=0s`로 비활성 가능 |
| Go API 응답 캐시 | 이번에 추가했다가 원복. 관련 환경변수도 제거 |
| 신뢰 프록시 IP | 로컬 구현·테스트 추가. 실제 운영 CIDR은 아직 설정하지 않음 |
| Cloudflare Cache/Rate Limiting Rules | 이 작업에서 계정 조회·생성·변경 안 함 |
| Caddy | 기존 정적 JS/CSS/vendor Cache-Control 유지 |
| 로고·파비콘 | 8개 HTML 페이지에 사용자가 제공한 PNG를 연결. 바이너리/이미지 재빌드·배포 필요 |

로컬 응답 캐시 원복 파일은 `/private/tmp/b2d-cache-rollback.qqtIx5`에 임시 백업했다. 임시 폴더는 장기 보관 위치가 아니며, 작업 디렉터리에 캐시 구현이 남아 있지 않아야 한다.

## 2. 먼저 확인할 것

1. `api.birth2death.com`의 관리 계정·Cloudflare Proxy 적용 여부·현재 Cache/Rate Limiting/WAF/Worker/Page Rules를 확인한다. DNS나 기존 룰을 추측으로 덮어쓰지 않는다.
2. 기존 광범위 `Cache Everything`, 캐시 키에서 query 무시, 원본 `no-store` 무시 설정이 있는지 확인한다. 여러 룰의 충돌·평가 순서도 검토한다.
3. 실제 원본 접근 경로·방화벽·Caddy와 앱 컨테이너 네트워크를 확인한다. 앱·DB 포트는 외부 공개하지 않는다.
4. 선택한 요금제의 캐시/속도 제한 조건·과금·로그 보존 비용을 확인한다. 이 문서는 유료 플랜 구매를 승인하지 않는다.

## 3. 1차 Cache Rules 정책

아래는 정책 명세다. 계정별 사용 가능한 필드와 실행 순서를 확인한 뒤 설정한다. 실제 Cloudflare 표현식이나 적용 완료 상태가 아니다.

| 우선 보호할 요청 | 정책 |
|---|---|
| Host가 해당 서비스가 아님 | 이 서비스 규칙 대상에서 제외 |
| `/v1`, `/v1/*` | BYPASS. 무료 데모 API도 포함 |
| `/mcp`, `/mcp/*` | BYPASS. 스트리밍·세션·POST 포함 |
| `/config.json`, `/issue-demo-key` | BYPASS |
| 인증 헤더(`Authorization`, `X-API-Key`)·Cookie가 있는 요청 | BYPASS. 공개 캐시와 혼합하지 않음 |
| GET/HEAD 이외 메서드 | BYPASS |
| 명시적으로 승인한 정적 파일 | 캐싱 후보. 위 제외 조건보다 느슨한 룰이 뒤에서 이를 덮어쓰지 않게 함 |

정적 파일 시작 범위는 실제 파일이 존재하는 `/styles.css`, `/shared.js`, `/map.js`, `/docs.js`, `/batch.js`, `/vendor/`의 자산, `/brand/b2d-geo-c1abd2177e38.png`다. 단순히 `.js`로 끝난다는 이유로 모든 경로를 허용하지 않는다. `/v1/foo.js` 같은 경로로 데이터가 공개 캐시에 들어가는 cache deception을 테스트한다.

- 원본의 캐시 금지 응답을 강제로 무시하지 않는다. 인증 응답·키 발급·설정은 브라우저용 `Cache-Control: private, no-store`도 배포 전에 추가/검증할 방어 항목이다. 현재 API 코드에 이 헤더가 전역 적용되었다고 가정하지 않는다.
- 초기 정적 TTL 제안은 기존 자산 정책과 맞춘 1시간. 브랜드 자산은 내용 해시 경로이므로 후속으로 1년·immutable도 가능하지만, 지금 Cloudflare에 적용한 값은 없다.
- `styles.css` URL에 브랜드 버전 query를 붙였다. query 전체를 무시하는 기존 CDN 룰이 있으면 이 갱신 기법은 효과가 없으므로 배포 때 기존 룰과 필요시 해당 CSS URL purge를 확인한다.
- 현재 HTML은 장기 캐싱하지 않는다. JSON은 기본적으로 캐싱될 것이라고 가정하지 않는다.
- 오류·Set-Cookie 응답을 저장하지 않는지 검증한다. 계정 설정으로 상태코드 TTL을 덮어쓰지 않는다.

[Cloudflare 기본 캐시 동작](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/), [Cache Rules 설정](https://developers.cloudflare.com/cache/how-to/cache-rules/settings/).

## 4. Rate Limiting 정책

캐싱은 재사용이고, 속도 제한은 요청량 통제다. 둘 다 필요하다. 캐시 HIT도 엣지 처리·네트워크 비용을 발생시키며 Go에 도착하지 않은 요청은 Go 제한으로 막을 수 없다.

- 엣지에는 IP 기반 기본 보호를 둔다. static과 API/MCP의 호출 패턴을 구분하고, 지도 로딩의 정상 요청 묶음을 차단하지 않도록 실제 로그의 정상 버스트를 측정한다.
- “1초 10회”는 일반 예시이며 이 서비스의 운영값으로 채택한 것이 아니다. 현재 Go 값 20/40도 전체 고객 트래픽 관측으로 재평가할 수 있다.
- 캐시 HIT를 카운팅에서 제외하지 않는 옵션·룰 순서인지 검증한다. Worker를 사용한다면 제한 검사가 cache lookup 앞에 와야 한다.
- 키별 제한은 기존 Go에 남긴다. IP를 바꾸더라도 같은 키의 호출을 제한한다. IP만으로 고객별 공정성·과금을 보장하지 않는다.
- 현재 Go 버킷은 프로세스 메모리다. 여러 서버를 띄우면 전역 한도가 아니며 재시작 시 초기화된다.
- 기존 버킷 맵은 유휴 청소만 있고 동시 활성 주체의 엄격한 최대 개수는 없다. 엣지 우회 차단과 메모리 관측이 필요하며 이번 변경이 모든 DoS 경로를 제거한 것은 아니다.
- health·MCP 연결 수·고비용 공간 쿼리에는 별도 원본 보호가 필요할 수 있다. 사용자별 속도 제한만으로 DB 동시 부하가 제한되지는 않는다.
- 429에는 Retry-After를 제공하고 클라이언트는 지수 백오프와 jitter로 재시도한다. 인증 실패나 무효 입력을 무한 재시도하지 않는다.

Worker의 rate limiting binding은 위치별 정책이며 정확한 전역 월 한도의 대체물이 아니다. [공식 설명](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).

## 5. 프록시 뒤 사용자 IP

설정 이름: `B2D_TRUSTED_PROXY_CIDRS`. 쉼표로 구분한 CIDR 목록. 기본은 빈 값이다.

구현 규칙:

1. 실제 연결 상대인 RemoteAddr가 신뢰 CIDR에 속하지 않으면 X-Forwarded-For를 무시한다.
2. 신뢰 상대일 때만 X-Forwarded-For를 오른쪽에서 왼쪽으로 읽는다. 첫 비신뢰 주소가 사용자 후보이며 그 왼쪽 값은 믿지 않는다.
3. 잘못된 주소·과도하게 긴 체인 등은 실제 연결 상대 IP로 돌아간다. IPv4-mapped IPv6는 정규화한다.
4. 설정 중 하나라도 잘못되면 전달 헤더 신뢰를 전부 끄고 경고한다. `/0` 전체 주소 허용 설정은 거부한다.

예시 주소를 운영 환경에 그대로 복사하지 않는다. Caddy의 실제 앱 방향 주소만 지정하고, 가능하면 전용 내부 네트워크와 좁은 `/32` 또는 `/128`을 사용한다. `0.0.0.0/0`, `::/0`, 무조건 모든 private subnet을 신뢰하는 설정은 사용하지 않는다.

### Caddy만 있는 경로

`인터넷 → Caddy → Go`에서 Go는 Caddy만 신뢰한다. Caddy가 외부 요청자가 공급한 전달 헤더를 그대로 신뢰하지 않는지 확인한다. 설정을 비워두면 헤더 위조에는 보수적으로 동작하지만 모든 고객이 Caddy 하나의 IP 버킷을 공유할 수 있다.

### Cloudflare를 앞에 두는 경로

`인터넷 → Cloudflare → Caddy → Go`는 두 신뢰 경계를 모두 설정해야 한다.

- Go 설정만 추가하면 Caddy가 보는 Cloudflare IP가 최종 사용자로 판정될 수 있다.
- Caddy는 공식 Cloudflare IP 범위 또는 검증된 전용 연결만 신뢰하게 구성하고, 원본 직접 접근을 방화벽/인증된 연결로 제한한다. IP 범위 갱신도 운영 책임이다.
- 신뢰 체인을 해석하는 Caddy 설정과 strict 파싱을 검토하고, Go에 어떤 X-Forwarded-For 체인을 전달할지 실제 요청으로 검증한다.
- `CF-Connecting-IP`를 무조건 Go에서 읽도록 바꾸지 않는다. 직접 원본에 접근한 공격자가 같은 이름의 헤더를 위조할 수 있다.

이 작업은 Caddy의 신뢰 설정·방화벽·DNS를 변경하지 않았다. [Caddy reverse_proxy 헤더 문서](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#headers)를 기준으로 배포 시 검증한다.

MCP 프로세스가 내부 HTTP로 API를 호출하는 경로에서는 Go가 MCP IP를 본다. 이는 이번 CIDR 기능만으로 해결되지 않는다. 외부 MCP 연결은 엣지에서 별도 제한하고 내부 API는 키별 제한을 유지한다. MCP에서 검증 없이 외부 헤더를 전달해 IP를 꾸미지 않는다.

## 6. API 캐시를 켜기 전 필요한 설계

단순 Cache Rule로 `/v1/*`를 캐싱하지 않는다. 먼저 다음을 보장하는 Worker 또는 동등한 게이트웨이 설계가 필요하다.

- HIT마다 키 유효성·scope·고객별 상품 범위·키 폐기·총량 확인.
- 같은 요청의 재시도에도 사용량 기록이 중복되지 않고 유실 정책이 명확함.
- 캐시 HIT와 MISS가 같은 과금 계약을 적용하고 Go와 이중 집계하지 않음.
- 서버가 검증한 release·as_of·time_basis·필터·권한/고객 범위를 cache key에 포함.
- 허가되지 않은 origin 직접 호출·위조 내부 서비스 토큰을 차단.
- 키 폐기·정정 release·비공개 canary·권한 회수·캐시 purge와 장애 처리가 테스트됨.

현재 meter는 비동기 best-effort 기록이다. 엄격한 유료 한도가 제품 요구라면 과금 원장/예약 처리 개선을 캐시와 별도 선행 작업으로 기록한다. `Sentry`는 오류 관측 도구이며 과금 원장이나 속도 제한 저장소가 아니다.

## 7. 배포 전·후 검증표

| ID | 검증 | 기대 |
|---|---|---|
| C01 | 서버 코드에서 응답 캐시 참조 검색 | 기존 체인만 존재, 응답 캐시 환경변수 없음 |
| C02 | Go auth/API 테스트와 race 실행 | 인증·제한·IP 파싱 회귀 없음 |
| C03 | 모든 HTML 로고·favicon URL과 PNG 조회 | 같은 원본 이미지, 200, image/png |
| C04 | 공개 정적 파일 반복 조회 | 같은 엣지 조건에서 HIT와 Age 확인 가능 |
| C05 | `/v1/*`, config, 키 발급, MCP 반복 조회 | CF cache HIT 없음, 인증/계측 정상 |
| C06 | A키·B키·무효/폐기키·scope 변경 | 서로 다른 권한에 캐시 유출 없음, 인증 TTL 정책 준수 |
| C07 | 공개 캐시를 먼저 채운 뒤 한도 초과 호출 | 엣지에서도 429/설정한 차단 응답; HIT를 보호에서 제외하지 않음 |
| C08 | 정상 지도 로딩·공유 NAT | 정상 트래픽을 잘못 차단하지 않음 |
| C09 | 원본 직접 접근·위조 전달 IP | 차단되거나 실제 상대 IP로 제한 |
| C10 | 고객 A만 버스트 초과 | 고객 B의 정상 요청은 같은 프록시 버킷에 묶이지 않음 |
| C11 | Cloudflare→Caddy→Go 실제 체인 | 로그에서 실제 IP 판정 확인, 민감값 로그 없음 |
| C12 | 이전/새 로고와 CSS 캐시 | 배포 후 새 URL·스타일 반영, 필요시 해당 URL만 purge |
| C13 | 과거 시점/정정/canary 후속 캐시 | 다른 버전이 섞이지 않고 MISS도 온라인 DB에서 조회 |

이 표는 완료 보고가 아니라 검증 계획이다. 로컬 테스트 결과와 Cloudflare·운영 테스트 결과를 별도로 기록한다. 로컬 테스트 통과를 C04–C12의 운영 검증 완료로 표시하지 않는다.

## 8. 배포와 되돌리기

- 정적 파일은 Go 바이너리에 embed되므로 단순 파일 복사만으로 실행 중 서비스가 바뀌지 않는다. 승인된 기존 빌드·배포 흐름으로 이미지를 다시 만들고 배포해야 한다.
- 로고는 이미지 내용을 바꾸지 않고 `brand/b2d-geo-c1abd2177e38.png`로 복사했다. 내용 해시 경로라 이전 아이콘의 브라우저 캐시와 충돌을 줄인다. 같은 PNG를 파비콘·Apple touch icon·공유 이미지에도 사용한다.
- Go 신뢰 CIDR 기능은 환경변수를 비우면 전달 헤더를 신뢰하지 않는 기본 모드로 돌아간다. 프록시 주소 변경 시 정책을 검토한다.
- Cloudflare 캐시 변경 문제가 생기면 대상 규칙을 BYPASS로 돌리고 관련 캐시를 표적 purge한다. 원본의 인증·계측은 계속 유지한다.
- 도메인·TLS·Caddy·전체 DB·현재 서비스 데이터를 이 작업 때문에 새로 만들거나 교체할 필요는 없다.

## 9. 이번 작업의 로컬 검증 결과

2026-09-12 작업 디렉터리 기준:

- `go test ./...` 통과.
- `go test -race ./internal/api ./internal/auth ./web` 통과. 프록시 위조 헤더·IPv4/IPv6·고객별 IP 버킷·키별 제한·브랜드 이미지 원본 해시·8개 페이지 연결을 포함한다.
- `internal/api/server.go`는 원래 코드와 동일하다. 서버 응답 캐시 코드·테스트 2개 파일과 환경변수 연결을 제거했다. 기존 인증 결과 캐시는 변경하지 않았다.
- 설치된 Chrome에서 8개 페이지 × 390/1280px × light/dark = 32가지 조합의 로고 로딩·크기·파비콘 연결을 확인했다. 테스트에서 외부 지도 타일과 API 호출은 차단했으므로 실서비스 지도 데이터 검증은 아니다.
- 설계문서 Mermaid 다이어그램 8개를 파싱하고 SVG로 렌더링했다. 문서 내 로컬 링크와 코드 diff 공백 검사도 통과했다.
- GitNexus 변경 분석은 프록시 처리와 관련된 공통 인증 실행 경로를 HIGH로 분류했다. 이를 숨기거나 운영 안전성 보증으로 바꾸지 않는다. 실제 CIDR·Caddy 체인·Cloudflare 경로 검증은 배포 전 남은 작업이다.

위 결과는 배포 전 로컬 검증 기록이다. 이후 운영 점검에서 기존 프록시·배포 설정에 별도 수정이 있음을 확인했으므로, 그 파일을 덮어쓰지 않고 앱 이미지와 명시적인 프록시 신뢰 설정만 별도 override로 배포한다. DB 마이그레이션이나 ETL은 실행하지 않는다. 실제 배포 완료·롤백 정보는 별도 배포 기록에 남긴다. Cloudflare 룰·DNS·원본 방화벽 변경은 이 배포 범위가 아니다.
